# 심해협곡 Stage 2 구현계획: 코드 조사와 잠수함 파손 상태

## 범위와 기준

2026-09-16 현재 코드를 읽고 작성한 **구현 전 계획**이다. 이번 작업에서는 코드를 변경하지 않는다. [Stage 2 레벨디자인](./deep-sea-stage2-level-design.md)의 다섯 구역, 중앙 닻, 탐험 미니맵, 세 필수 발견물을 목표로 한다. 이번 추가 결정에 따라 심해협곡의 생명력 표현은 **하트 HUD를 사용하지 않고 잠수함 외형 3단계로 표현**한다. 기존 기획의 하트 문구와 현재 구현은 아래 정합성 항목에서 구분한다.

## 2. 체력·피격·실패 시스템 상세 조사

| 질문 | 현재 코드 |
|---|---|
| 하트 3개가 실제 구현됐는가? | Scene의 `health = 3` (`createDeepSeaGame.ts:39`), Host의 React `health = 3` (`DeepSeaGameHost.tsx:28`), HUD의 채운/빈 하트 출력 (`100`)이 있다. |
| 피해 횟수는 어디서 관리하는가? | 별도 피격 횟수나 `damageState`는 없다. Scene의 남은 `health`를 1씩 감소시킨다 (`createDeepSeaGame.ts:345-348`). |
| 적 접촉 피해 위치는? | `updateHazards()`에서 플레이어와 적 중심 거리가 43 이하일 때 판정 (`createDeepSeaGame.ts:307-355`). Phaser Physics collision은 사용하지 않는다. 환경 장애물 피해 코드는 없다. |
| 무적시간은? | `INVINCIBLE_MS = 1300`, `invincibleUntil`과 게임 시간 비교 (`createDeepSeaGame.ts:7,40,345-346`). 피격 시 컨테이너 alpha tween 100ms 왕복 5회 (`349`). 요구한 1~1.5초 범위에 이미 든다. |
| 초기화 위치는? | `health = 3`, `invincibleUntil = 0`은 Scene 필드 초기값. Host state도 3으로 시작한다. `onRetry`는 App의 `startAdventureGame()`을 통해 새 `runId`를 만들고, `AdventureGameShell`이 `key={runId}`로 재마운트된다 (`App.tsx:1926-1948,2684`). 별도 Scene reset 함수는 없다. |
| 실패·결과 연결은? | `health <= 0`이면 `finished = true`, 입력을 비우고 `onFailure()` 호출 (`createDeepSeaGame.ts:350-354`). Host가 실패 overlay와 재도전/지도 버튼을 표시한다 (`DeepSeaGameHost.tsx:132-143`). 결과의 발견·코인 수만 표시하며 health 수치는 표시하지 않는다. 실패 문구는 현재 “하트가 모두 사라졌어요” (`136`). |

**재사용 판단:** 내부 `health: 3→2→1→0`과 피해 차단·실패 호출은 **REUSE**. 상태 매핑 `health 3 → damageState 0`, `2 → 1`, `1 → 2`, `0 → failure`를 한 곳의 순수 함수로 두는 것이 우선안이다. 잠수함 상태 이미지는 **EXTEND**, 하트 HUD와 하트 중심 문구는 **REPLACE**한다. Stage 2 첫 구현에서는 `stage2.ts:78`의 수리 픽업을 제거하거나 비활성화한다. `healthRestore` 코드 경로는 향후 수리용으로 보존 가능하나, 수리 시에도 texture 동기화를 거쳐야 한다. 이 결정이 심해협곡 공통 규칙인 만큼 Stage 1에도 잠수함 외형 표현을 적용하고 하트 HUD를 제거해야 일관된다.

## 3. 잠수함 표현과 피격 피드백

현재 플레이어는 **이미지·sprite sheet가 아닌** ellipse, circle, triangle 3개를 담은 Phaser Container다 (`createDeepSeaGame.ts:138-144`). 방향별 파일, 이동 animation, texture key가 없다. 방향은 컨테이너의 각도를 0/90/180/270으로 돌린다 (`153-155`). 따라서 현재 상태에서 단순 `setTexture()`는 불가능하다.

구현안은 컨테이너를 이동·카메라 추적 대상으로 유지하면서 자식 도형을 단일 Phaser Image로 바꾸는 것이다. 같은 기준점·크기·방향을 가진 정상/경미 파손/심각 파손 texture를 preload하고, `health` 변경 시 Image의 texture만 교체한다. 이동과 방향 전환은 컨테이너에 남긴다. 세 장의 4방향 이미지는 현재 회전 방식과 충돌하므로 우선 제작하지 않는다. 한 장의 오른쪽 기준 이미지를 회전해도 글자·비대칭 무늬가 어색하지 않은지 아트 검수한다. 필요할 때만 방향별 확장한다.

피격 순서: 적/장애물 접촉 → 무적 여부 확인 → health 1 감소 → `damageState` 파생 → texture 교체 → 가벼운 위치/각도 흔들림과 alpha blink, 작은 단발 충격 이펙트 → 1.3초 무적. 기존 blink tween을 재사용하고, 흔들림은 이동 컨테이너가 아닌 자식 이미지에 짧게 적용해 타일 이동·카메라 좌표를 흔들지 않는다. 마지막 피격은 critical 유지 또는 짧은 파손 프레임 뒤 이동 정지와 기존 실패 overlay로 이어간다. 폭발 파티클·필터는 쓰지 않는다. 첫 피격과 두 번째 피격에만 한 줄 피드백을 허용하고 반복 popup은 피한다.

`health`는 Scene의 단일 진실 값으로 유지한다. Host에 health를 남기더라도 HUD에는 숫자/게이지를 표시하지 않고 피격 메시지 등 필요한 이벤트에만 쓴다. Scene 생성 직후 정상 texture와 Host 초기값을 맞춘다. 재도전 시 새 Scene에서 `health=3`, `damageState=0`, 무적 타이머 0으로 시작한다. 회복 기능을 나중에 켜면 `health` 증가와 texture 변경도 같은 함수로 처리한다.

`src/assets/adventure/deep-sea/` 폴더는 현재 없다. 현재 Scene은 잠수함, 적, 보상, 지형을 Phaser 도형/텍스트로 그린다. `src/assets/adventure/relics/parts|completed|silhouettes/deep-sea/`는 지역 유물 UI 자산이며 잠수함 플레이어 에셋이 아니다. `public/player_hit.png`, `src/assets/adventure/health_restore.png`와 다른 지역의 피격 에셋은 존재하지만 심해 잠수함에 맞는지 확인되지 않았고 현재 deep-sea 코드에서 사용하지 않는다.

## 5. 레벨·시스템 구현 방법

1. **맵/구역:** 기존 36×36 크기를 유지하고 배치를 레벨디자인 기준으로 재구성한다. 시작 산호숲, 중앙 닻 허브, 난파선, 암흑협곡, 고대유적, 열수지대를 구역 ID와 랜드마크 좌표로 명시한다. 중앙·보조 연결을 만들고 막다른 길마다 보상을 지정한다. 벽 집합 방식은 초기 데이터에 활용할 수 있으나, 표현은 반복 가능한 타일 기반 자산으로 전환한다.
2. **목표·보상:** 현재 `DeepSeaDiscoveryKind = coral|statue|chest`는 Stage 1/2가 공유하고, Stage 2에서 상자가 필수 목표다 (`types.ts:3`, `stage2.ts:58-62`, `DeepSeaGameHost.tsx:15-19`). Stage별 목표 목록과 `requiredForExit` 또는 별도 필수 ID 목록을 도입해 난파선 기록 장치·유적 조각·열수지대 발견물만 출구 조건으로 센다. 일반 상자는 보너스로 분리한다. 희귀 발견도 선택 기록으로 분리한다. 코인 8~12, 상자 2, 아이템 1을 배치하되 수리 효과는 제외한다.
3. **부분 미니맵:** `renderFog()`는 현재 시야만 그리며 방문 상태를 저장하지 않는다. 방문 타일 집합, 발견 랜드마크, 발견물 상태를 Scene/맵 데이터로 만들고 Host의 작은 미니맵 또는 Phaser HUD로 그린다. 초기 전체 지도 공개 금지. 소나의 일시 확장과 영구 방문 기록을 분리한다. 출구 활성화 후 출구 아이콘을 강조한다.
4. **적:** 현재 상어 chase는 벽을 무시하고 플레이어 좌표로 직선 이동하므로 타일 통로 기반 경로 또는 짧은 시야·추적 시간·복귀 규칙이 필요하다. 문어도 경고→짧은 돌진→대기 상태를 명시한다. 산호숲의 느린 상어와 후반 위험을 별도 config로 배치한다. 화면 밖 업데이트 최소화는 유지하되 재진입 시 위치·상태가 예측 가능하도록 한다.
5. **환경 기믹:** `isFloor()`는 정적 벽만 읽는다 (`createDeepSeaGame.ts:104-107`). 암벽문은 3~4초 주기 상태와 열린 동안의 통과 판정, 닫힘 전 경고·끼임 방지 규칙을 추가한다. 해류는 이동 중 방향 힘 또는 다음 타일 선택에 작용시키며 조작을 완전히 빼앗지 않도록 한다. 열수 분출구는 이번 레벨에서 강한 시각 랜드마크이며, 피해 기믹 포함 여부는 구현 착수 전에 결정한다. 세 기믹 모두 기존 단일 피격 함수와 무적시간을 공유해야 한다.
6. **출구·결과:** 세 필수 목표 획득 후 `onExitUnlocked`와 출구 접근 클리어를 재사용한다. 실패 시 Scene의 `finished`와 Host overlay를 재사용하고, 문구를 잠수함 파손으로 교체한다. 실패 때 Stage 완료·보상 지급이 발생하지 않는 현재 경로를 유지한다.

## 6. 진행·저장과 정합성

- `App.tsx:2022-2065`의 `finishAdventureRun`이 클리어 시 코인과 Stage 진행을 저장한다. `runId` 중복 지급 방지도 있다. Scene/Host의 발견·픽업·damageState는 현재 런 중 상태이며 영구 저장되지 않는다.
- [전체 기획](./deep-sea-game-design.md)은 심해도감 자동 등록과 실패 후 기록 유지를 제안하지만, 현재 `App.tsx`의 `discoveredSpeciesIds`는 공룡 종 도감이다. 심해 발견물을 여기에 섞지 말고 별도 저장 계약을 정해야 한다. 이번 아이 테스트에서 영구 도감이 필요한지, 런 중 기록만으로 충분한지 결정한다.
- `minigameConfig.ts:7,13`의 deep-sea 진입 비용은 0이다. `App.tsx:1935-1948`에서 0 비용 진입/재도전은 새 run을 만든다. 보상은 Host에서 코인만 전달한다 (`DeepSeaGameHost.tsx:62-69`). 일반 아이템을 실제 인벤토리에 지급하려면 `MinigameRunRewards`와 허용 아이템 풀을 검토해야 한다.
- [레벨디자인](./deep-sea-stage2-level-design.md)은 이전 공통 규칙을 인용해 하트 3개·피격 시 하트 감소라고 적었다. [전체 기획](./deep-sea-game-design.md), [Phaser 계획](./deep-sea-phaser-plan.md), [목업 계획](./deep-sea-mockup-plan.md)에도 하트 문구가 있다. **이번 결정이 우선**이며, 기존 문서는 과거 목업 기준으로 읽는다. 이번 단계에서 대규모 수정하지 않고 실제 구현 시 문구를 정리한다.
- 이전 문서에는 Stage 2가 30×30/필수 2개라고 되어 있지만 현재 코드는 이미 36×36/필수 3개다. 새 레벨 기획과는 숫자가 맞으나 **발견물의 종류와 구역 위치는 맞지 않는다**. 소나 기본 3회와 5~7분 목표는 이전 기획 기준으로 남아 있으며 체감 검증이 필요하다.

## 7. 구현 Phase

| Phase | 구현 내용 | 완료 기준 |
|---|---|---|
| 1. 데이터·맵 | Stage 2 구역/허브/랜드마크/목표·보상 ID, 36×36 경로 재배치 | 시작·세 필수 목표·출구가 모두 도달 가능하고 막다른 길에 의미가 있음 |
| 2. 잠수함 파손 | 3장 에셋, 컨테이너 자식 Image, health↔damageState, 하트 HUD·실패 문구 변경 | 1·2회 피격의 외형 차이가 뚜렷하고 3회째 실패, 1.3초 동안 중복 피격 없음 |
| 3. 탐험 정보 | 구역 시각 테마와 중앙 닻, 랜드마크, 방문 기록·부분 미니맵 | 허브와 구역을 구별하고 미탐험 길을 추측할 수 있음 |
| 4. 적·장애물 | 상어 복귀/벽 대응, 문어 경고, 암벽문, 해류, 열수 표현 | 위험의 예고와 회피 경로가 있고 문·해류가 목표를 막지 않음 |
| 5. 보상·결과 | 필수/선택 분리, 코인·상자·아이템·희귀 발견, 출구/실패/재도전 | 선택 보상은 클리어 조건에 영향 없고 실패 시 보상 중복 지급 없음 |
| 6. 아이 테스트·성능 | 구형 iPad Pro 1세대, 30fps 목표, 위치 기억·파손 인지 관찰 | “한 번 더 맞으면 위험”을 외형만 보고 이해하고 길찾기 실패 신호가 반복되지 않음 |

Phase 1~5에서 직접 관련된 순수 규칙·맵 도달성 테스트를 추가하고, 코드 변경 시 프로젝트의 검증 정책에 맞춰 필요한 최소 검증을 수행한다. 이 문서 작성 단계에서는 테스트·빌드·브라우저 검증을 하지 않는다.

## 8. 아이 테스트에서 추가 관찰할 점

- 첫 피격 직후 잠수함 손상을 스스로 알아차리는가?
- 두 번째 피격 후 “한 번 더 맞으면 위험하다”는 행동 변화가 생기는가?
- 하트 HUD 없이 외형과 짧은 피드백만으로 현재 상태를 파악하는가?
- 피격 원인을 설명할 수 있고, 연속 접촉이 한 번의 피해로 처리되는가?
- 랜드마크를 이용해 중앙 허브로 돌아오고, 미탐험 길과 위험 우회 경로를 선택하는가?

## 9. 구현 전 확정할 사항과 큰 기술적 위험

결정할 사항: (1) 소나 3회와 미니맵의 정보 범위, (2) 열수 분출구의 피해 기믹 포함 여부, (3) 선택 아이템의 실제 효과와 심해도감 영구 저장 범위, (4) Stage 1도 동시에 외형형 생명력으로 바꿀지 적용 시점. 권장안은 심해협곡 공통으로 하트 HUD를 제거하고, Stage 2 첫 버전의 수리 픽업은 제외하는 것이다.

1. **경로/동적 장애물:** 정적 벽 검사에 문·해류를 얹으면 플레이어가 갇히거나 필수 목표 접근이 불가능해질 수 있다. 문 상태별 경로와 복구 경로를 검증해야 한다.
2. **적 이동과 피격 공정성:** 현재 상어·문어는 벽을 무시한 직선 이동이며 충돌은 중심 거리다. 좁은 통로에서 예고 없이 피격하거나 벽 너머에서 따라올 위험이 있다.
3. **상태·보상 동기화:** Scene health, Host 표시, 잠수함 texture, 실패/재도전, 수리 픽업, 런 보상이 서로 분리돼 있다. 모든 피해·회복을 단일 상태 변경 경로로 모으고 runId별 중복 지급을 확인해야 한다.
